# 审核结论

- High | Task 1 Step 6-9、`packages/extension/src/handlers/query.ts` 入口 | 计划把 `resolveTargetOptional` 接在仅判断 `args.pattern == null` 的路径上，但 MCP 的 `liftQueryRefToTarget` 会在扩展收到请求前把 `@ref` 翻译成 `index + snapshotId`，所以该入口没有覆盖计划声称的真实 `@ref` 链路。 | 真正的 `vortex_query({ mode: "style", pattern: "@..." })` 经 server 翻译后到扩展时没有 `pattern`，有 `index`；当前 Step 8 的条件会进入 `resolveTargetOptional`，这一点可工作，但 Step 6 的测试只手工传 `index`，没有验证 MCP helper 的输出能被 server 翻译后正确送达扩展，也没有验证 frame/tab 字段和错误传播。若实现者只按测试通过实现了任一侧，另一侧仍可能断线。 | 增加跨包 handler/协议级接线测试，至少把 `liftQueryRefToTarget` 输出送入 server 的 target 翻译，再断言扩展收到 `index/snapshotId/frameId`；扩展测试另断言 `resolveTargetOptional` 的 `boundTabId/boundFrameId` 被实际用于 `getActiveTabId` 和 `buildExecuteTarget`。不要只测纯 helper。
- High | Task 3 Step 6、`packages/extension/tests/query-style.test.ts` | 计划明确要求验证 `attr → groups → executeScript args[2]` 的接线，但给出的测试没有实现这条调用链，且后续只在“若无测试”时建议补测，不能作为计划的硬性步骤。 | `styleProbeFunc(..., ["typography"])` 纯函数测试即使 handler 仍传 `["typography","box","paint","motion"]`、传空数组或完全不传第三参也会全绿；这正是本仓库上一轮“公式对、调用点错”的失效模式。Step 5 的 handler 回归测试也未给出 `args[2]` 断言。 | 把 handler 级测试列为必做：填 `attr: "typography"`，断言 `executeScript.mock.calls[0][0].args[2]` 恰为 `["typography"]`；再用非法组断言 handler 拒绝。把变异验证从条件性说明改成强制步骤。
- High | Task 4 Step 6-7 | `mode=tokens` 的 handler 测试只 mock `executeScript` 返回值，未断言传入的 `func` 是 `tokensProbeFunc`、`args` 是 `[pattern,maxPerGroup]`，也未验证 mode 白名单和 pattern 必填语义。 | handler 即使错误地调用了 `styleProbeFunc`、传错 pattern、把 `maxResults` 当成每组上限，测试仍会使用 mock 返回值而通过；真实站点因此可能永远拿不到 token 或截断错误。 | 断言 `executeScript` 调用的 `func` 和 `args`，至少覆盖默认上限、显式 `maxResults`、pattern 过滤；增加 `mode=tokens` 缺 pattern/非法 mode 的入口测试。
- High | Task 4 Step 1/3/8、`tokensProbeFunc` 分类设计 | “按值形态优先、名字其次”的实现与测试没有覆盖关键分类冲突，且 `classify` 的顺序会把带颜色的阴影值先归为 `color`，不是 `shadow`。 | `0 1px 2px rgba(0,0,0,.1)` 不匹配当前颜色正则开头条件，但会命中 shadow 正则；然而 `0 1px 2px #000` 也会命中 shadow。更严重的是任意值形如 `rgba(...)` 本身先归 color，若 token 是阴影只有颜色部分而没有前置长度则会被归错；`var(--shadow)` 又完全回落名字。计划没有规定或测试这些边界，产出的设计系统分组会不稳定。 | 明确 shadow/gradient/颜色的语法优先级，使用覆盖长度与颜色的完整 shadow 规则，并增加 `0 1px 2px rgba(...)`、纯颜色、`linear-gradient(...)`、`var(--shadow)` 的断言；同时说明“同一 token 多类型”如何处理。
- High | Task 2 Step 1-4、Task 6 Step 5 | “无上限祖先循环”只要遇到第一个非透明背景就停止，但没有处理祖先背景图优先级和透明层叠语义；计划要求的 `contrastStatus` 可能与实际 painted 背景不一致。 | 若近祖先有 `background-image`，随后更远祖先有不透明 `background-color`，代码会先把 status 设为 `background-image`，但仍继续上溯，遇到颜色后 break；结果 status 保留 image、background 却是更远颜色，返回互相矛盾的数据。若元素自身 `backgroundImage !== "none"` 但同时有可计算的纯色，直接标 unknown 也是保守但未在验收中说明。 | 建立明确的 painted 背景模型：遇到第一个产生绘制的背景层即停止，或分别返回背景图/颜色及不可判定原因；增加近祖先 image、远祖先 color、元素自身 image+color 的测试，不以一个渐变用例代替层叠语义。
- High | Task 4 Step 1、Task 4 Step 3 | `new Function("return " + tokensProbeFunc.toString())()` 不能证明注入函数在真实 MAIN world 中自包含，因为测试仍使用当前 jsdom 全局的 `window/document/getComputedStyle`，并且替身通过 `vi.spyOn(window, ...)` 只替换了 jsdom 对象。 | 若实现误引用模块级常量，`new Function` 通常能抓到；但若实现引用测试环境/扩展环境提供的全局、依赖 jsdom 特有行为，测试仍可能绿。更关键的是真实 Chrome 的 `CSSStyleDeclaration` 自定义属性枚举、属性顺序和 `getPropertyValue` 行为由浏览器实现，fake 只实现了 `length`、迭代器和 getter，无法发现 host 类型转换、不可迭代、异常值等差异。 | 自包含测试应在隔离 global 中执行序列化函数，并显式提供最小真实注入 API；另加真实浏览器验收。对 token 枚举不要只依赖 fake，使用页面内实际 `style.setProperty` 的 Chrome 测试验证自定义属性能被枚举/读取，或把可移植的“枚举属性名”适配层单独测试。
- Medium | Task 2 Step 1、jsdom 祖先用例 | 第 10 层祖先测试不能可靠证明真实 Chrome 的“painted background 到第 10 层”行为；jsdom 不执行布局和绘制，`getComputedStyle` 对继承、默认透明值、背景图解析与 Chrome 不同。 | 用例只检查 style 属性返回值，无法复现真实的 stacking/painting；jsdom 可能返回 `rgba(0, 0, 0, 0)` 或简单字符串，而不是 Chrome 的计算样式。测试即使通过也不能证明 gamma.app 场景已修复，反之也可能因为 jsdom 的默认值导致假失败。 | 把 jsdom 测试限定为循环边界和返回判据的单元测试；把第 10 层背景、渐变和实际 WCAG 值列入 Task 6 真浏览器硬验收，并保留一个明确的 Chrome 结果断言。
- Medium | Task 3 Step 3、具体技术判断 | 驼峰转短横线对 `borderRadius`、`backgroundImage` 是正确的，但对带厂商前缀的 `webkitTextFillColor` 会生成 `-webkit-text-fill-color`，这点本身通常正确；计划没有覆盖前缀，也没有处理已经是短横线的属性名。 | 当前属性列表没有 `webkitTextFillColor`，以后扩展属性时若传 `-webkit-text-fill-color` 会被再次转换为 `-webkit--text-fill-color`；同时 `ms` 前缀的 CSSOM 约定也可能产生不同结果。技术判断不能只用 borderRadius/backgroundImage 两个正例证明通用转换安全。 | 增加转换函数的单元测试并规定输入只允许 camelCase，或让 `pick` 同时接受已规范化 CSS 名称；至少覆盖 `borderRadius`、`backgroundImage`、`webkitTextFillColor` 和已带 `-` 的名称。
- Medium | Task 4 Step 3、tokens roots 读取 | 计划只遍历 `:root` 和 `body` 的 `getComputedStyle`，但把 body 覆盖解释为“后写胜出”，没有说明主题根、组件根或 shadow root，也没有验证 CSS 自定义属性的继承和覆盖。 | gamma.app 的 token 可能挂在主题容器而非 body；`getComputedStyle(body)` 只能看到继承到 body 的变量，未被继承或挂在中间主题节点的变量会漏掉。即使 `:root/body` 有变量，按两个 host 合并也无法代表页面所有设计变量，`total ≥ 600` 的真站验收会把实现绑定到单一站点结构。 | 明确 D 的扫描范围和“设计 token 面”的召回边界；至少扫描文档根、body、主题根候选，或在返回中声明只覆盖 root/body。真站验收不应把 600 个作为能力正确性的唯一门槛。
- Medium | Task 4 Step 1、Task 5 Step 1 | 计划背景说 pattern 可空、schema 要求 `pattern` 必填、实现却以 `pattern === "*"` 或 `pattern.toLowerCase()` 处理，没有定义缺省值。 | 用户按路线 D 预期调用 `mode=tokens` 不传 pattern；当前 schema 会先拒绝，若绕过 schema，handler 还可能把 `undefined` 传入探针并在 `pattern.toLowerCase()` 处报错。计划内部“pattern 可空”“required pattern”“pattern=* 全量”三种契约冲突。 | 统一契约：建议 tokens 的 pattern 可选，handler 将缺省归一化为 `"*"`，并在 schema、handler、探针测试、真站验收中使用同一语义。
- Medium | Task 5 Step 1-5 | 公开 schema 的 `mode` 增加 `tokens`，但 `pattern` 仍是全局 required；这会阻止 tokens 的自然无元素调用，且 description 只写“pattern=*”没有明确 style 的 @ref 与 tokens 的无 pattern 差异。 | `vortex_query({mode:"tokens", pattern:"*"})`可用，但计划 §5/路线 D 明确提到 pattern 可空；客户端无法按“空 pattern 取全量”使用接口，文档和实现会分叉。 | 改为按 mode 语义在 handler 中校验，或拆 schema/使用 oneOf 表达 tokens 的可选 pattern；补 schema 级断言，而不是只测字节预算。

## 总评

这份计划不能直接执行。最少必须先修正四处：第一，补上 Task 1 的跨 MCP/server/extension 接线验证，不能只用两组纯函数测试；第二，把 Task 3 的 `attr → groups → executeScript args[2]` handler 测试改为强制步骤；第三，为 Task 4 增加真实 handler 参数/func 接线测试，并重写 token 探针的自包含与 Chrome 行为验证；第四，统一 tokens 的 `pattern` 契约并明确背景 painted 语义。路线 A+D 作为第一阶段可以成立，但 D 不是“调研样式”的完整替代，B/C 应保留为不宣称最终级联结果的可选证据面。当前未发现 bench 或 observe 渲染代码直接消费 `wcagAA/wcagAAA`，这是通过仓库 grep 查证的结果；外部消费者的 truthy 兼容风险仍需发布说明和契约测试覆盖。
