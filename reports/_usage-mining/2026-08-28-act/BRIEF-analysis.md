## 本轮的核心分析动作：看恢复轨迹，不看单点

对每个失败样本，**必须把它后面的调用一起抽出来**，回答：

1. **调用方失败后做了什么？** 换 selector 重试？改用 observe 拿 ref？换工具（evaluate 旁路）？还是直接放弃？
2. **重试了几次才成功？** 有没有根本没成功的？
3. **恢复动作是不是错误信息里建议的那个？** 如果错误 hint 说"用 observe ref"，调用方实际却去改 CSS selector 硬试——说明 hint 没被采纳，要么不可执行，要么不可信。
4. **同一个失败形状是否跨会话反复出现？** 跨会话重复 = 不是某个人某次手滑。

## 判据：什么才算工具缺陷（A 类）

满足任一即可标 A，但必须有证据：

- 错误信息给出的恢复路径，**调用方照做后仍然失败**（hint 是错的或不可执行）
- 调用方需要 **3 次以上尝试**才恢复，或大量直接放弃转 evaluate 旁路（说明工具没提供可行的成功路径）
- 同一形状跨 **3 个以上会话**重复出现（说明是系统性的，不是个别误用）
- 失败本可以被工具自己消化（例如工具已有足够信息自愈却选择报错）

反过来，**下列情况仍判 B/C，不要硬凑 A**：调用方一次就恢复了、错误 hint 照做即成功、失败源于站点自身状态（弹窗遮挡、元素真的没了）。

## 归因四问（任一为否即毙掉候选）

1. 失败样本的**实际入参**里，真的出现了你认为出问题的那个参数吗？
2. 你认为漏传/漏读的字段，下游**真有消费者**吗？（读 handler 源码确认）
3. 在这些失败样本的实际入参下，改前 vs 改后行为**真的会不一样**吗？
4. 修改后的代码路径，真实环境里**真的会走到**吗？答不了就写"只能靠 live 验证"。
