## 硬性方法要求（这些是本项目反复踩坑换来的，不许省）

1. **禁止只凭日志文本下根因结论。** 每个你认定的缺陷，必须在**真实浏览器**里复现一次，
   贴出复现步骤和实际返回。复现不了的，明确写「未复现」，不要当成已确认缺陷。
   本项目历史上多轮「日志/静态分析得出的根因」被真站 spike 推翻，这是最贵的教训。
2. **必须区分三类**，并对每个发现明确标注属于哪一类：
   - A 工具缺陷：vortex 行为错误或诚实性不足（这才是我们要修的）
   - B 模型误用：调用方式不对（比如把自然语言当 CSS 选择器传）——可能要改 schema 描述或错误提示，不是改行为
   - C 站点脾气/环境：目标页面本身如此，或环境问题（端口占用、扩展没重载）——不是缺陷
   高错误率**不等于**缺陷。让 act 去点一个本来就不存在的元素，报错是正确行为。
3. **根因要做归因分析，不是复述现象。** 「超时因为元素没附着」不是根因，
   「为什么没附着 / 为什么等待策略没兜住 / 为什么错误提示把调用方引向死路」才是。
   给出 `file:line` 证据链，行号要按当前代码核对过。
4. **不要为了凑数量报缺陷。** 宁可只报 1 个坐实的，不要报 5 个待验证的。
   如果结论是「没有真缺陷，都是 B/C 类」，那就如实这么写——这是可接受且有价值的结论。
5. **不改产品代码**，不新建 worktree。可以为复现写临时脚本或临时 fixture，用完说明放在哪。

## 交付物

写入 `reports/_eval/next-iteration-2026-08/FINDINGS-usage-log.md`，每个发现包含：

- **现象**：日志里的证据（哪个 transcript、调用参数、返回什么）
- **分类**：A/B/C，附理由
- **复现**：真实浏览器里的步骤与实际结果；未复现就写未复现
- **根因**：归因分析 + `file:line` 证据链
- **解决方案**：改什么、为什么这么改、有没有更省的做法、可能的副作用
- **置信度**：高/中/低，以及还有哪些假设没验证

末尾附一节「**已排除**」：你查过但判定为 B/C 类的，各一两句说明——
这节和发现同样重要，它防止下一轮重复排查。
